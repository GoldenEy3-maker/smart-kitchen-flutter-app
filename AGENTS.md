# Smart Kitchen — инструкции для агента

Flutter-приложение для учёта продуктов в холодильнике, рецептов, меню на неделю и списка покупок.
Данные полностью локальные (Hive), без сети и авторизации. Один язык интерфейса — русский.
Продуктовые требования и описание экранов: `docs/design-spec.md`.

## Команды

```bash
flutter analyze                                           # анализ, должен быть чистым
dart format .                                             # обязательно после правок
flutter test                                              # тесты
dart run build_runner build --delete-conflicting-outputs  # json_serializable + auto_route
flutter gen-l10n                                          # после правки app_ru.arb
```

После изменения `*_model.dart` или роутов — запусти `build_runner`. После правки `.arb` — `gen-l10n`.

## Архитектура

Четыре слоя, зависимости направлены вниз (единственное исключение — внутри `domains`):

- **`lib/app`** — сборка приложения: DI-регистрация, роутер (`auto_route`), layout'ы, страницы (`pages`), реализации навигаторов.
- **`lib/features/<feature>`** — экран или сценарий. Своё состояние (BLoC), UI (`views`, `widgets`), может иметь свои `domain/usecases` для композиции нескольких доменов и `domain/entities` для view-модели.
- **`lib/domains/<domain>`** — предметная область (`products`, `categories`, `fridge`): `domain`, `data`, `params`, `error`, `di`, `navigation`.
- **`lib/core`** — инфраструктура и дизайн-система: тема, виджеты, l10n, логирование, storage, `Either`, `Failure`, базовый `UseCase`.

Правила зависимостей:

- `core` не зависит ни от `domains`, ни от `features`.
- `domains` зависит от `core` и, как исключение, от других `domains`. Домен никогда не знает про `features` и `app`. Условия и обоснование — в `lib/domains/AGENTS.md`.
- `features` зависит от `domains` и `core`, но **не** от других `features`. Переход в другую фичу — только через интерфейс навигатора в `domains/<domain>/navigation` с реализацией в `app/navigation`. Эталон: `domains/products/navigation/products_navigator.dart`.
- `app` может зависеть от всего — это слой сборки.

Конвенции каждого слоя лежат рядом с кодом, читай ближайший файл к тому, что правишь:

| Файл | О чём |
|---|---|
| `lib/domains/AGENTS.md` | entity, model, params, data source, repository, use case, failure, cross-импорты |
| `lib/features/AGENTS.md` | BLoC (события, состояние, обработчики), views и widgets фичи |
| `lib/core/AGENTS.md` | дизайн-система и токены, l10n, `Either`/`Failure`, storage, логирование |
| `lib/app/AGENTS.md` | pages, роутер, порядок DI-регистрации, навигаторы |

## Стиль

Действует везде, вне зависимости от слоя:

- Двойные кавычки в строках и импортах (`prefer_double_quotes`).
- Импорты внутри проекта — всегда абсолютные, `package:smart_kitchen_flutter_app/...`, даже для файла в той же папке: относительные импорты запрещены правилом `always_use_package_imports`. Директивы `part` — единственное исключение.
- В каждой папке барель-файл (`views.dart`, `usecases.dart`, `entities.dart`, ...), импортируй через него, а не напрямую по файлам. Новый файл — добавь экспорт в барель.
- Никаких магических чисел, цветов и шрифтов: только токены `AppSpacing`, `AppRadius`, `AppDuration` и `context.theme.colors` / `context.theme.text`.
- Ни одной строки для пользователя в коде: всё через `context.l10n` и `app_ru.arb`.
- Всё, что можно сделать immutable, делается immutable: `final` поля, `const` конструкторы, `extends Equatable` для сравнимых по значению типов.
- SDK — Dart 3.12, dot-shorthand для enum разрешён и используется (`mainAxisAlignment: .center`). Не переписывай это в полную форму.
- Комментарии — только там, где нужно объяснить неочевидное решение или ограничение. Не описывай словами то, что видно из кода.
- Набор правил анализатора — `very_good_analysis`, отключённые правила и причины перечислены в `analysis_options.yaml`. Замечание линтера исправляется по существу, а не глушится через `// ignore`; если подавление всё-таки нужно, рядом обязателен комментарий с причиной (`document_ignores`).

## Чего делать нельзя

- Добавлять или обновлять зависимости в `pubspec.yaml` — сначала спроси.
- Править сгенерированные файлы: `*.g.dart`, `*.gr.dart`, `core/l10n/app_localizations*.dart`.
- Рефакторить или «попутно улучшать» код, который не относится к текущей задаче.
- Менять архитектурные границы (перекладывать файлы между `core` / `domains` / `features`) без явной просьбы.
- Обращаться к репозиториям из presentation напрямую — только через use case.
- Бросать исключения из `data` наружу — только `Either<Failure, T>`.
- Создавать файлы документации, README или тесты, если об этом не просили.
- Оставлять `flutter analyze` с ошибками или неотформатированный код.

## Как работать над задачей

Сначала опиши план: какие файлы затронешь и что в них изменится, — и дождись подтверждения, прежде чем писать код. Держи диф минимальным: одна задача — одно изменение.

Новый код пиши не с нуля, а по эталону: вертикальный срез домена `products` и фича `product_form` каноничны, повторяй их структуру целиком, включая барели и DI-регистрацию.

Тестов в проекте пока нет. Если задача — писать тесты, используй `flutter_test`, а для BLoC — `bloc_test` (его нужно добавить в `dev_dependencies`, спроси перед этим).
